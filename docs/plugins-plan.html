3 · The auth pivot — how Google connects without 2FA

The old path is dead for your constraints. Verified today from Google's own help pages: “App passwords can only be used with accounts that have 2-Step Verification turned on.” No 2FA ⇒ no app password ⇒ no IMAP/SMTP login at all. So Blueprint v3 §9's app-password line and the Gmail plan's §3 checklist are retired.

The replacement is OAuth with one specific publishing-status trick — verified today against Google's developer docs and a documented working example:

  • One Google Cloud project. OAuth consent screen: user type External, publish status set to “In production” — and deliberately left unverified. The 7-day refresh-token expiry from the blueprint's “OAuth trap” applies only to projects left in Testing status; production status (even unverified) issues non-expiring refresh tokens for sensitive and restricted scopes. This is the documented, reproducible escape.
  • The price of skipping verification is small and personal-scale: a one-time “Google hasn't verified this app → Advanced → proceed” interstitial per account during connect (you click it once), a 100-user cap (2–3 accounts total — irrelevant), and consent screens showing the app name without branding.
  • Scopes minted while the project was in Testing keep their 7-day clock — we connect after flipping to production, and the token inspector field (refresh_token_expires_in absent = immortal) is the proof-check in build step 2.
  • Only standard rules remain afterwards: tokens die if unused 6 months (a personal assistant will never idle that long), if you change the account's password, or if you revoke — all recoverable by re-connecting in the settings pane.

4 · What a plugin is — the framework, not just a list

Every entry in the settings rail is an instance of one shape, so adding plugin #7 is data, not surgery:

  • Manifest (server-side, TypeScript like personas): id, display name, tool names it contributes, auth kind (oauth / mcp / api-key), required scopes, approval defaults per capability class, icon/category.
  • Connection store: one row per (plugin, account). Carries account label (“Agni” vs “Nachiketh”), status, token blob (server-side only), last health check, granted-at. New numbered migration; feeds a settings protocol frame so the app draws the pane from live server state — not hardcoded UI.
  • Capability matrix — the core of the whole plan. Every plugin action belongs to a class, and each (plugin × account) pair sets a policy per class:
Capability classAgent's own accountYour accounts
Search / read / listFreeFree
Draft / stage (nothing leaves the box)FreeFree
Send / publish / create events / share filesFree — it's its mailboxApproval per action, bubble previewed; “always allow this recipient/file-type” unlocks later
Delete / modify existingFree (except permanent delete — scope-omitted)Approval per action, and mostly unnecessary
Payments (none of these plugins touch money today)Always ask, as ever — carried from the guardrails list

Repo-rules amendment this plan proposes: AGENTS.md currently reads “Shell, file writes outside scratch, email sends, and payments are approval-gated.” It needs one clause: …except sends from Agni's own configuring account, which are ungated by owner decision (2026-10-17). Shell, payments, and anything touching your accounts stay gated. Without editing the rule file, the build would violate its own documented guardrails.

Untrusted-input rule unchanged and now load-bearing: the agent will read mail/meetings/doc comments written by strangers while holding uncapped power in its own account. A mail body, a Granola transcript, a Drive comment — all stay data-with-provenance; instructions inside are flagged, never executed. Its unrestricted-but-own-account reach is exactly why the injection rule is a guardrail, not a nicety.

8 · Known limits, on the record

Unverified interstitialThe one-time “Google hasn't verified this app” screen during connect is cosmetic and uncontroversial; a real verification review is the alternative and nobody should want that paperwork for a one-user app.
Granola plan tierIf the free tier is what's active, MCP sees personal notes (30 days) only — team-space notes need the Business plan. The roster table in §5 says which plan buys which reach; check the workspace settings once.
Gmail quotasREST sending caps (per-user/day) are generous beyond personal scale and the send ledger keeps them visible; the agent's own account hitting a soft cap is a non-event, not an incident.
Two Google accounts, one projectThe 100-user cap is per-project; both accounts consuming separate slots is fine. If a third appears someday (a “family” account?) it's still nowhere near the ceiling.
